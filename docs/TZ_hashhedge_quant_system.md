# ТЗ: система мониторинга и бэктеста под правила проп-компании HashHedge

> Версия 2 (2026-09-23). Что изменилось относительно v1 — раздел 12.

Ты работаешь как senior quant/backend инженер. Цель — построить личную систему, которая:
1. собирает и надёжно хранит рыночные данные по инструментам HashHedge (рынок Crypto + TradFi: крипто- и TradFi-перпы; позже — рынок US Stocks);
2. бэктестит стратегии **строго по правилам челленджа HashHedge** и оптимизирует их по **вероятности прохождения челленджа**, а не по доходности;
3. в live-режиме показывает в веб-интерфейсе скринер всех инструментов с индикаторами, **калиброванной вероятностью** успеха лонга и шорта и разбором сетапа;
4. отправляет сигналы в Telegram (личный бот и/или приватный канал) с планом сделки и размером позиции под текущее состояние счёта.

Исполнение сделок — **ручное** (у проп-платформы нет API). Система не торгует сама.

## 0. Как работать

- Работай **по фазам** (раздел 9). В начале каждой фазы — короткий план, в конце — прогон тестов и отчёт о том, что сделано и что осталось.
- **Не выдумывай правила проп-фирмы.** Всё, что не описано в разделе 2, вынесено в конфиг и в «Открытые вопросы» (раздел 11). Если нужно допущение — делай его консервативным (хуже для трейдера) и помечай `# ASSUMPTION`.
- Модуль правил (`propsim`) пишется **test-first**: сначала тесты из раздела 2.6, потом код.
- Никакого look-ahead: сигнал считается только по закрытым барам, исполнение — не раньше открытия следующего бара.
- **Корректность данных важнее полноты.** Бар или сделка, не прошедшие проверки раздела 3.2, помечаются и не участвуют ни в сигналах, ни в исполнении. Молча заполнять пропуски запрещено.
- Цены и объёмы из API храни/парси без потери точности (Decimal/строки на входе, float64 допустим только в расчётном слое).
- Отдавай законченные файлы, а не патчи-фрагменты.

## 2. Правила HashHedge (источник: hashhedge.gitbook.io/hashhedge-user-guide)

Всё ниже — в `config/challenge.yaml`, ничего не хардкодить.

### 2.0 Рынки

- **Crypto + TradFi** (`market=crypto_tradfi`): крипто-терминал, торговля 24/7. Перпы на криптовалюты, акции, ETF, металлы и энергоносители. Все 172 инструмента из CSV — здесь.
- **US Stocks** (`market=us_stocks`, фаза 8): отдельная платформа (>11 000 тикеров NYSE/NASDAQ), только двухстадийный челлендж, свои правила (раздел 2.4). TradFi-перпы на акции (TSLAUSDT и т.п.) к этому рынку **не относятся**.

Правила propsim (граница дня, автозакрытие, лимит акций) выбираются по колонке `market`, а не по `asset_class`.

### 2.1 Стадии

| Правило | Стадия 1 | Стадия 2 | Трейдер |
|---|---|---|---|
| Целевая прибыль | 8% | 6% | нет |
| Дневная потеря | 5% | 5% | 5% |
| Общая потеря | 10% | 8% | 8% |
| Мин. торговых дней | 5 | 5 | нет |
| Срок | не ограничен | не ограничен | не ограничен |
| Макс. плечо | 1:5 | 1:5 | 1:5 |
| Доля прибыли | — | — | 80% (90% с Profit Split) |

Одностадийный: цель **10%**, дневная 3%, общая 6%, мин. 3 торговых дня, срок не ограничен, плечо 1:5, на стадии Трейдер — дневная 3%, общая 6%, доля прибыли 80% (90%).

Все проценты — **от размера счёта (стартового баланса)**, в долларах фиксированы. Размеры:
- двухстадийный — 5k, 10k, 25k, 50k, 100k, 200k;
- одностадийный — 5k–100k;
- US Stocks — 5k–100k.

150k («Titan») есть в таблице дневного лимита, но отсутствует в списке размеров двухстадийного челленджа. Держать его в конфиге (раздел 11).

### 2.2 Дневной лимит (точная модель)

- `daily_loss = equity_now - balance_at_day_start`
- `equity = balance + unrealized_pnl` (по всем позициям, нетто). **Unrealized PnL считается по Mark Price**: по документации платформа использует mark price для unrealized PnL и ликвидации.
- `balance` меняется только при закрытии позиции, списании комиссии, начислении funding.
- `daily_floor = balance_at_day_start - daily_limit_usd`, где `daily_limit_usd = account_size * daily_loss_pct` (фиксирован, не зависит от текущего баланса).
- Провал: `equity <= daily_floor` в любой момент.
- **Граница дня — окно, а не точка.** Crypto+TradFi — **00:00–00:10 UTC+4 (= 20:00–20:10 UTC)**; US Stocks — 08:00–08:10 UTC+4 (= 04:00–04:10 UTC). В этом окне фиксируется `balance_at_day_start`; точный момент внутри окна неизвестен.
  - К какому дню относятся события внутри окна (закрытия, funding в 20:00 UTC у инструментов с интервалом 4h/1h), задаёт параметр `reset_window_mode: new_day | old_day | both`.
  - По умолчанию `both` (`# ASSUMPTION`, самый консервативный): событие проверяется против лимитов обоих дней.
  - Система не планирует входы и выходы внутри окна.
- Открытые позиции переносятся, их floating PnL уже в equity → новый день может начаться с частично съеденным лимитом.
- Комиссии входят в дневную потерю; funding двигает balance скачком.
- Daily Loss Protection (опция): покупается только при оформлении челленджа, срабатывает 1 раз за жизнь счёта, работает на всех стадиях, включая Трейдер. При пробое дневного лимита — закрыть все позиции, снять ордера, обновить дневной лимит, продолжить.
- Daily Loss Reset — то же действие. Покупается после провала (24 ч на оплату), только стадии 1–2.
- Обе опции — флаги в конфиге, по умолчанию выключены. На общий лимит не действуют.
- Дашборд HashHedge обновляется не в реальном времени. В live опираться на собственный расчёт equity (раздел 8.2), а не на цифры дашборда.

### 2.3 Общий лимит

- `total_floor = account_size * (1 - max_loss_pct)` — **режим `static` по умолчанию**; поддержать также `trailing` (от максимума equity/balance) как опцию, т.к. в документации явно не указано (см. раздел 11).
- Провал: `equity <= total_floor` (equity по mark price) → принудительное закрытие, окончательный провал. Protection/Reset на него не действуют.

### 2.4 Торговые ограничения

- Рынок Crypto + TradFi: только перпы, спота нет.
- Плечо ≤ 5 (`notional <= 5 * equity` — точную формулу маржи уточнить, см. раздел 11).
  - Режимы маржи isolated/cross; одновременно только один.
  - Сменить режим можно только после закрытия всех позиций и отмены всех ордеров.
- Лимиты позиции на инструмент (по notional с плечом): `max_per_lot` (одна позиция) и `max_total` (суммарно на инструмент). Значения — колонки `max_per_lot_usd` / `max_total_usd` в `config/instruments.csv` (сверены с документацией HashHedge на 2026-09-23; перед прогонами сверять с терминалом).
- Торговля в выходные и на новостях разрешена.
- Запрещено: арбитраж, манипуляции. **Система никогда не предлагает встречные позиции на разных счетах/челленджах.**
- **Особенности терминала, влияющие на модель исполнения:**
  - SL/TP срабатывают по Last или Mark price — выбирается при выставлении; в мобильном терминале всегда Mark;
  - Limit-SL (trigger price + order price) может не исполниться, если цена проскочила уровень и не вернулась. Система предлагает только stop-market SL;
  - контракты, зарезервированные лимитным ордером (в т.ч. лимиткой на закрытие), недоступны для SL/TP: SL/TP сработает, но не исполнится. В плане сделки не совмещать лимитный выход и SL/TP на одном объёме;
  - ликвидация — по Mark Price (Est. Liq. Price).
- **US Stocks (только `market=us_stocks`, фаза 8):**
  - не больше 10 000 акций на тикер;
  - buying power = balance × 5 на весь счёт (а не плечо на позицию);
  - новые позиции блокируются в 23:55 UTC+4, все позиции закрываются автоматически в 23:59 UTC+4, перенос невозможен;
  - комиссия 0.04% от сделки, минимум $1.

  Эти правила **не применяются** к TradFi-перпам (`asset_class` = equity/etf на рынке `crypto_tradfi`).

### 2.5 Комиссии, funding, выплаты

- Maker 0.01%, taker 0.03% от полного notional (с плечом), при открытии **и** закрытии.
- Funding — переменный. По документации HashHedge он «exchanged between traders»; собственная ставка платформы неизвестна (раздел 11).
  - По умолчанию брать историю funding **основного источника (Binance USDⓈ-M)**; Bybit — только для сравнения.
  - Применяется к позициям, открытым в момент начисления. Формула: `fee = qty * mark_price(t_funding) * rate`. Лонг платит при rate > 0, шорт — при rate < 0.
  - Mark price на момент начисления: поле `markPrice` в REST `/fapi/v1/fundingRate` или open 1m `markPriceKlines`.
  - Время начислений — только фактические `fundingTime` из истории. Интервал у символов разный (8h/4h/1h) и меняется биржей на ходу: на 2026-09-23 у 78 из 172 инструментов он не 8h.
  - `fundingTime` приходит с миллисекундным смещением (`…800001`) — округлять до секунды.
- Торговый день = календарный день (граница — см. раздел 11, по умолчанию та же 20:00 UTC), в который **открыта** хотя бы одна позиция. Позиция, открытая в один день и закрытая в другой, — один торговый день.
- Стадия пройдена: цель достигнута **и** набрано мин. число торговых дней. Метрика цели (`balance` или `equity`) — параметр, по умолчанию `balance` (консервативно). Новая стадия стартует с баланса = `account_size` (`# ASSUMPTION`).
- Выплаты (Трейдер):
  - 80%/90% прибыли;
  - выплата доступна, когда прошло 14 дней, счёт в прибыли и **все позиции закрыты**;
  - следующий запрос — не раньше 14 дней после исполнения предыдущего;
  - максимум $10 000 на счёт за 14 дней, минимум $100.
- На стадии Трейдер одновременно может торговаться только один челлендж каждого номинала (в рамках рынка).
- Цена челленджа — параметр `challenge_fee_usd` по типу и размеру (для расчёта EV).

### 2.6 Обязательные тест-кейсы propsim (Boost, $10 000, лимит $500)

Каждый пример — отдельный unit-тест, проверяющий balance / unrealized / equity / daily_loss по шагам:

1. **Обычный день.** Старт 10 000 → открытие (fee 5) → 9 995 → позиция −400 (equity 9 595, DL −405) → funding −50 (balance 9 945, equity 9 545, DL −455) → позиция −445 → equity 9 500 → **FAIL**.
2. **Баланс выше старта.** Старт дня 10 700, лимит всё равно 500, floor 10 200. Та же последовательность → FAIL при equity 10 200.
3. **Две позиции.** Fees −8 → A −400, B +200 → equity 9 792, DL −208 → не провал.
4. **Убыточная позиция переносится.** Новый день: balance 10 000, unrealized −300, equity 9 700, DL −300 → funding −50 → fee 3 → вторая позиция −147 → equity 9 500 → FAIL.
5. **Прибыльная позиция переносится.** Новый день equity 10 300 (DL +300), floor 9 500 → откат до −300, funding −50, ещё −150 → equity 9 500 → FAIL.

Плюс тесты:
- пробой общего лимита;
- Daily Loss Protection срабатывает один раз;
- подсчёт торговых дней по границе дня;
- отказ ордера при превышении `max_per_lot`/`max_total`/плеча;
- **equity по mark price:** фитиль last-цены ниже floor при mark выше floor — не провал; при `equity_price_source=last` — провал;
- **окно сброса 20:00–20:10 UTC:** закрытие и funding внутри окна для каждого режима `reset_window_mode`;
- **funding от mark price на момент начисления**, а не от цены входа;
- конфиг одностадийного челленджа (10% / 3% / 6%, 3 дня).

Автозакрытие акций в конце сессии — в фазе 8 (рынок `us_stocks`).

### 3.1 Маппинг инструментов (`config/instruments.csv`)

Колонки: `hh_symbol, base, asset_class, market, underlying_type, max_per_lot_usd, max_total_usd, primary_source, binance_um, binance_um_mult, bybit_linear, bybit_linear_mult, binance_spot, binance_spot_mult, binance_onboard, bybit_launch, history_start, notes`.

- `asset_class`: `crypto | equity | etf | metal | energy` — класс для стратегий и фильтров.
- `market`: `crypto_tradfi` (все 172) | `us_stocks` (фаза 8). По этой колонке выбираются правила propsim.
- `underlying_type`: из `exchangeInfo` Binance (`COIN`, `EQUITY`, `KR_EQUITY`, `COMMODITY`, `PREMARKET`) — для календаря сессий базового рынка.
- `binance_onboard` / `bybit_launch`: время листинга текущего контракта (UTC, ISO 8601), как его отдаёт биржа.
- `history_start`: начало валидной истории **текущего** актива на основном источнике. По умолчанию = `binance_onboard`; ручные исключения — только после проверки, с объяснением в `notes`.

Правила:
1. **Внутренний ключ везде — `hh_symbol`.** Биржевые тикеры живут только в слое коллекторов/backfill. В ClickHouse хранить `hh_symbol`, `source`, `source_symbol`.
2. **Множители контрактов.** `1000PEPEUSDT`, `1000SHIBUSDT`, `1000FLOKIUSDT`, `1000BONKUSDT`, `1000RATSUSDT` (Binance) и `SHIB1000USDT`, `1000PEPEUSDT`, `1000FLOKIUSDT`, `1000BONKUSDT`, `1000RATSUSDT` (Bybit) котируют 1000 единиц базового актива.
   - Нормализация при записи: `price_norm = price / mult`, `qty_norm = qty * mult`, `tick_norm = tick / mult`, notional не меняется.
   - Сырые данные в Parquet — без нормализации (как пришли), нормализация — только при загрузке в ClickHouse.
   - Точность: нормализованная цена за 1 единицу доходит до ~10⁻⁵ при шаге ~10⁻¹⁰ (PEPE). Хранить Float64 или Decimal со scale ≥ 12; `Decimal(18,8)` недопустим.
   - Какой масштаб цены у самого HashHedge (за 1 или за 1000 единиц) — открытый вопрос (раздел 11). Хранить нормализованно за 1 единицу, масштаб HashHedge — отдельный параметр `hh_price_mult` (дефолт 1).
3. **Разные тикеры у бирж:**
   - `SHIB` → Bybit `SHIB1000USDT`;
   - `BEAMX` → Bybit `BEAMUSDT`;
   - `PUMP` → Bybit `PUMPFUNUSDT` (Bybit `PUMPUSDT` был другим активом и закрыт 2025-06-03);
   - `DODOX` → Binance spot `DODOUSDT`.

   Считать их одним инструментом только после сверки цены (п. 5). Все пары Binance↔Bybit сверены по нормализованной цене 2026-09-23.
4. **Нет на Bybit (11):**
   - XPT, XPD, NATGAS, COPPER, PAYP, NOK;
   - FET, JOE, DODOX, SPELL — контракты Bybit закрыты;
   - OPENAI — PreLaunch.

   **Нет Binance spot:** ZETA, BSV, RATS, HYPE, LAB, RIVER, UB, MON, LIT (спотовый `LITUSDT` — это Litentry в статусе BREAK), XMR (спот делистингован) и все TradFi.
5. **Валидация при старте и раз в сутки:**
   - тикер существует и в статусе TRADING / Trading; `contractSize`/multiplier совпадает;
   - `onboardDate` / `launchTime` не изменился относительно CSV. Иначе это переименование, релистинг или переиспользование тикера: алерт, инструмент исключается из сигналов до ручного обновления `history_start`;
   - данные до `history_start` в ClickHouse не загружаются (сырые файлы в Parquet остаются как есть). Известные случаи:
     - `LITUSDT`: Litentry 2021–2025, затем «замороженные» бары, Lighter с 2025-12-23 17:30 UTC;
     - `PUMPUSDT`: другой актив 2025-04…07, pump.fun с 2025-07-10 07:30 UTC;
     - `ICPUSDT`: архив начинается раньше `onboardDate`, но это тот же актив (проверено) — `history_start` выставлен вручную;
   - пары Binance↔Bybit: медианное расхождение нормализованной цены за последние 24 ч по 1m close меньше порога, иначе алерт и пометка `mapping_suspect`.
     - Порог по группе: 0.3% для `crypto_major` и TradFi, 0.6% для `crypto_alt`.
     - На 2026-09-23 у неликвидных альтов медиана по 1h close при корректном маппинге доходит до 0.30% (DUSK).
   - делистинг/переименование тикера — алерт, данные не удалять.
6. **TradFi-перпы** (акции, ETF, металлы, энергоносители):
   - листинг на Binance — 2025-12-11 … 2026-06-08, на Bybit — 2026-03 … 2026-07;
   - торгуются 24/7, но вне сессии базового рынка ликвидность падает на порядок, и цена в эти часы не опирается на базовый рынок. Пример: TSLAUSDT — $108M оборота в четверг 2026-09-17 против $6M в субботу 2026-09-19; в субботу 8% минут без сделок и 30% свечей с O=H=L=C. XAU: $2.56B против $0.16B;
   - календарь сессий — по `underlying_type`: `EQUITY` — NYSE/NASDAQ, `KR_EQUITY` — KRX, `COMMODITY` — CME/ICE, у `PREMARKET` базового рынка нет;
   - сигналы по TradFi вне сессии и в выходные по умолчанию выключены (`tradfi_off_session_signals: false`). Параметры стратегий — отдельные по `asset_class`.
7. **Минимальная история и группы параметров:**
   - инструмент участвует в оптимизации, только если с `history_start` у него есть ≥ 180 дней 1m-данных на основном источнике (параметр). Короткие — только в live-мониторинге, с пометкой в алерте;
   - **параметры оптимизируются пулом по группе**, а не по отдельному символу: `crypto_major` (crypto с `max_per_lot_usd >= 100000`), `crypto_alt`, `tradfi`;
   - на 2026-09-23 ≥ 180 дней есть у 17 из 36 TradFi. С учётом hold-out 6 мес. (раздел 7) ни у одного TradFi нет даже одного полного окна train, поэтому TradFi до накопления истории — только live-мониторинг с пометкой в алерте;
   - 8 крипто-инструментов (LIT, MON, LAB, RIVER, ASTER, UB, LINEA, WLFI) не набирают 6 мес. train + 2 мес. test + 6 мес. hold-out и участвуют только в пуле своей группы.
8. **Выбор источника по символу:** `primary_source` из CSV.
   - **Один источник на весь ряд инструмента в рамках прогона.** Переключение Binance → Bybit внутри ряда даёт ступеньку базиса и ложные пробои у индикаторов.
   - Если у основного источника нет данных за период, инструмент исключается из бэктеста на этот период плюс окно прогрева индикаторов.
   - Bybit — кросс-проверка и резерв live-потока; сигналы по резервному источнику помечаются `source=bybit`.
   - `source` записывается в каждую строку.

### 3.2 Корректность данных (обязательные проверки)

1. **`history_start`.** Всё, что раньше, не загружается в ClickHouse и не участвует в расчётах (правило 3.1.5).
2. **«Замороженные» бары.** В периоды остановки или делистинга Binance отдаёт минуты с volume = 0 и O=H=L=C.
   - Серия из ≥ `halt_min_bars` таких минут подряд (параметр, по умолчанию 60) получает флаг `halted` целиком.
   - На `halted` барах сигналы не считаются, ордера не исполняются, индикаторы их не получают.
   - Одиночные бары с нулевым объёмом на неликвидных инструментах — норма (флаг `zero_vol`). Как их обрабатывают индикаторы, согласуется с TradingView в golden-тестах (раздел 6).
3. **Пропущенные минуты.** Реестр гэпов с причиной: `listing`, `relisting`, `exchange_maintenance`, `source_outage`, `unknown`.
   - Заполнение без флага запрещено; синтетические бары (`synthetic=1`) не используются для исполнения.
   - Приёмка «0 необъяснённых гэпов» = нет гэпов с причиной `unknown`.
4. **Разбор архива data.binance.vision.**
   - CSV бывают с заголовком и без (старые файлы — без).
   - Время: futures klines — миллисекунды; spot с 2025-01-01 — микросекунды; `bookDepth` — строка даты.
   - Скачивать строго по шаблону имени `<SYMBOL>-<dataset>-<period>.zip`: в листингах встречаются посторонние файлы, например `aggTrades/BTCUSDT/part-00000-….zip`.
   - Каждый файл проверять по `.CHECKSUM` (SHA-256). Манифест загруженных файлов (путь, sha256, размер, время загрузки) — в PostgreSQL.
5. **Дубли и версии.** Приоритет: архив > REST > WS (колонка `version`). Live-бары предварительные: на T+1 они сверяются с архивом data.binance.vision, расхождения попадают в отчёт и заменяются архивными.
6. **aggTrades.** Полнота проверяется по непрерывности `agg_trade_id` (и `first/last_trade_id`), а не по времени. `is_buyer_maker=true` ⇒ агрессор-продавец (знак для CVD).
7. **Время.** Только биржевые timestamps событий, не локальные часы; NTP на VPS.
8. **Отчёт качества данных** по инструменту входит в отчёт бэктеста: доля `halted` / `zero_vol` / `synthetic`, гэпы по причинам, расхождение с Bybit.

## 4. Архитектура и стек

```
Binance/Bybit WS ──> collector (Python, asyncio) ──> Redis Streams ──┬─> writer ──> ClickHouse
                                                                     └─> signals (Python) ──┬─> Redis (live state, pub/sub) ──> api
                                                                                            ├─> Telegram bot
                                                                                            └─> PostgreSQL (сигналы, журнал)

data.binance.vision / REST ──> backfill (Python) ──> raw Parquet (S3/MinIO) + манифест ──> rebuild ──> ClickHouse
                                                          │
                            research / backtest / montecarlo / calibration (Python: DuckDB/Polars по Parquet)
                                                          │
                            PostgreSQL (конфиги, прогоны, реестр испытаний, модели калибровки)

api (FastAPI, REST + WebSocket)      <── ClickHouse, PostgreSQL, Redis
web (Vue 3 + TS, Lightweight Charts) <── api
```
- **collector (Python 3.12, asyncio, orjson):** WS-коннекторы с reconnect/heartbeat, публикация в Redis Streams. Допустимы 2 инстанса на разных VPS (дедуп через `version` в ClickHouse). **Gap-detector** периодически ищет дыры в 1m и догружает их через REST. Переписывать коллектор на Go — только если замеры в фазе 6 покажут, что Python не справляется.
  - Режим `auto`: если WebSocket фьючерсов Binance не отдаёт данные (бывает из-за сетевых фильтров), коллектор переключается на REST-поллинг закрытых 1m-свечей и mark-свечей раз в минуту (`collector/binance_rest.py`).
- **Redis Streams:** буфер между collector, writer и signals (consumer groups, `MAXLEN`). Отдельный брокер не нужен — Redis уже в стеке.
- **ClickHouse:** `ReplacingMergeTree(version)`, `PARTITION BY toYYYYMM(ts)`, `ORDER BY (hh_symbol, source, ts)` плюс колонка `source_symbol`; кодеки `DoubleDelta` для ts, `Gorilla`+`ZSTD` для Float64.
  - **Materialized views на сырых вставках не использовать.** MV срабатывает на каждую вставку, а ReplacingMergeTree удаляет дубли только при слиянии частей. Повторная загрузка, второй коллектор или догрузка гэпов навсегда задвоят volume/CVD старших ТФ.
  - Старшие ТФ (5m/15m/1h/4h/1d) агрегируются из дедуплицированных 1m в `quant` — один код для бэктеста и live. Для UI и Grafana — запросы с `FINAL`.
  - Сделки в ClickHouse удаляются по TTL через N дней: источник истины — Parquet.
- **Raw Parquet архив** (неизменяемый, по дням) — источник истины; из него ClickHouse полностью пересобирается скриптом `rebuild`. У архива есть манифест (раздел 3.2.4).
- **research / backtest** читают Parquet напрямую через DuckDB/Polars; ClickHouse для них не обязателен.
- **PostgreSQL:** инструменты, конфиги стратегий, прогоны бэктестов, сделки, результаты MC, манифест архива.
  - **Реестр испытаний** — каждая проверенная конфигурация: параметры, хэш датасета, версия кода, метрики. Нужен для поправки на множественное тестирование (раздел 7).
- **Redis:** последние значения индикаторов, состояние счёта для live, дедуп алертов, Streams.
- **Python 3.12:** Polars, DuckDB, NumPy, Numba (горячие циклы propsim), pydantic для конфигов, pytest.
- **api (FastAPI):** REST для истории/отчётов/журнала, WebSocket для live-обновлений скринера (подписка на Redis pub/sub). Использует тот же пакет `quant`.
- **web (Vue 3 + TypeScript + Vite):** Pinia, TanStack Table (скринер), TradingView **Lightweight Charts** (open source) для графиков, Tailwind. SPA раздаётся через Caddy.
- **Доступ:** Caddy с HTTPS; вход один пользователь — пароль (argon2) + TOTP, сессия в httpOnly cookie; либо закрыть за VPN (WireGuard/Tailscale). Порты ClickHouse/Postgres/Redis наружу не открывать.
- **Мониторинг (с фазы 6):** Prometheus + Grafana — лаг данных по символу, число гэпов, реконнекты, отставание consumer group, расхождения live с архивом. Алерт «нет данных N минут».
- **Деплой:** docker-compose (без k8s), бэкапы ClickHouse через `clickhouse-backup` в S3.

Структура репозитория:

## 5. Движок бэктеста и propsim

- Событийный, шаг — 1m бар.
  - Сигналы — на ТФ стратегии (закрытие бара ТФ).
  - Исполнение — не раньше open следующего 1m бара, плюс задержка ручного исполнения `exec_delay` и slippage.
  - `exec_delay` — распределение, по умолчанию равномерное 1–10 мин от закрытия бара сигнала (параметр; `0` — для сравнения).
- **Какие цены где используются:**
  - исполнение ордеров — по last price (1m klines);
  - SL/TP-триггер — параметр `sl_tp_trigger: last | mark`, по умолчанию `last` (`# ASSUMPTION`). В плане сделки указывается тот же тип;
  - **equity и проверка лимитов — по mark price** (`markPriceKlines` 1m). Параметр `equity_price_source: mark | last`; `last` — стресс-сценарий, т.к. фитили last-цены на альтах глубже, чем у mark.
- **Внутрибарная консервативность:**
  - equity для проверки лимитов в баре считать по худшей mark-цене (low для лонгов, high для шортов, по всем позициям одновременно);
  - если в одном баре достижимы и SL, и TP — исполняется SL (`intrabar_resolution: sl_first`). Для инструментов с aggTrades есть режим `ticks`: порядок определяется по сделкам внутри бара. Доля таких неоднозначных сделок — в отчёте;
  - при пробое лимита — провал фиксируется в этом баре, позиции закрываются по цене, соответствующей floor (не лучше).
- **Ордеры:**
  - market — taker + slippage;
  - limit — maker, fill только при прохождении цены сквозь уровень, не при касании;
  - stop-market — taker + slippage;
  - limit-SL — возможное неисполнение: fill, только если цена вернулась к order price. По умолчанию система предлагает только stop-market SL.
- **Slippage** — модель по `bookDepth`: глубина на стороне исполнения в пределах ±0.2%/±1% в момент исполнения, отдельно по инструменту и часу. Фоллбэк — `max(1 tick_norm, k * ATR_1m)`. Плюс поправочный коэффициент к фиду HashHedge (раздел 11).
- На барах `halted` и `synthetic` исполнения нет.
- Funding — в фактические `fundingTime`, от `qty * mark_price` (раздел 2.5).
- В окне сброса 20:00–20:10 UTC входы и выходы по сигналам не планируются. События внутри окна обрабатываются по `reset_window_mode` (раздел 2.2).
- Проверки перед открытием: плечо, `max_per_lot`, `max_total`, режим маржи, минимальный размер ордера инструмента (если расчётный размер меньше — сделка не открывается).
- Выход: лог событий (открытие/закрытие/fee/funding/day_reset/fail/pass) → Postgres + Parquet.

### Risk governor (общий для backtest и live)

Параметры в конфиге стратегии, по умолчанию консервативные:
- `risk_per_trade` — доля **оставшегося** расстояния до ближайшего floor (daily или total), по умолчанию 10%; плюс абсолютный потолок в % от счёта.
  - Следствие: при таком сайзинге счёт приближается к floor геометрически и практически никогда его не пробивает — челлендж «зависает».
  - Поэтому P(pass) определяется только внутри горизонта H (раздел 7).
- `soft_daily_stop` — прекратить новые входы, если дневная потеря ≥ X% от дневного лимита (по умолчанию 60%).
- `max_concurrent_positions`, `max_correlated_exposure` (напр. суммарный риск по альтам).
- `flatten_before_reset` — опция закрывать позиции не позже 19:59 UTC, до окна сброса (сравнить в бэктесте с/без).
- `target_lock` — после достижения цели стадии: новые сигналы игнорируются, недостающие торговые дни добираются **минимальными позициями** (минимальный notional на самом ликвидном инструменте, мгновенное закрытие), чтобы не рисковать результатом.
- Учёт комиссий в расчёте размера: риск сделки = расстояние до SL + round-trip fees + ожидаемое проскальзывание.

## 6. Стратегии

- `baseline_random` — случайные входы с тем же risk governor. **Эталон:** стратегия считается полезной, только если P(pass both) статистически значимо выше baseline.
- `confluence_v1` — порт Pine-движка:
  - состав: HTF-тренд (EMA200 / структура), BOS/CHoCH, liquidity sweep, RSI (Wilder, RMA) и дивергенции (обычные и скрытые), объём/RVOL, VWAP/AVWAP, ATR-стоп, взвешенный скор 0–100, порог входа — параметр;
  - режимы long/short с отдельными параметрами (асимметрия рынка: у шорта шире ATR-стоп, быстрее тейк; шорт — только при медвежьем HTF);
  - **порт без look-ahead.** HTF-данные — только закрытые бары старшего ТФ (аналог `request.security(..., lookahead=barmerge.lookahead_off)` со сдвигом `[1]`). Пивоты, BOS/CHoCH, sweep и дивергенции подтверждаются только через `right` баров: время сигнала = время подтверждения, а не бар пивота.
- Дополнительные фильтры (флагами): ADX-режим, funding/OI-перегрев, CVD-дивергенция.
- **Объёмные индикаторы и границы:**
  - CVD 1m — из `taker_buy_volume` свечей Binance (все инструменты);
  - VWAP — по барам (hlc3 × volume), а не по сделкам. Якорь `vwap_anchor: utc_day | prop_day`: `utc_day` = сессия TradingView с 00:00 UTC (для паритета), `prop_day` = 20:00 UTC;
  - дневные бары (1d) — граница 00:00 UTC; агрегаты «проп-дня» (от 20:00 UTC) считаются отдельно.
- **Паритет индикаторов.** Golden-тесты RSI/EMA/ATR/ADX/VWAP против эталонных значений TradingView (CSV-фикстуры с фида `BINANCE:<SYMBOL>.P`).
  - Допуск **относительный** 1e-6.
  - Сравнивать после прогрева ≥ 25×period либо считать с того же стартового бара, что и TradingView.
  - Для RMA-индикаторов (RSI, ATR, ADX) прогрева 10×period недостаточно: остаток расхождения (13/14)^140 ≈ 3·10⁻⁵.
- Интерфейс стратегии: `on_bar(ctx) -> list[Signal]`, где `Signal` содержит side, entry type/price, SL (тип и триггер), TP(ы), score, reason. Никакого доступа к будущим барам (enforce через API контекста).

## 7. Оценка и оптимизация

### Метрики (главные — первые)
1. **P(pass stage1), P(pass stage2), P(pass both)** — в пределах горизонта H (параметр, по умолчанию 90 дней на стадию). Исходов три: pass / fail / unresolved, и все три показываются.
2. Распределение причин провала: daily vs total.
3. Медиана и p90 дней до прохождения каждой стадии.
4. **EV челленджа** = P(pass both) × E[выплаты за горизонт H на стадии Трейдер с учётом 80/90%, лимита $10k/14 дней, условия «все позиции закрыты» и вероятности слива] − `challenge_fee_usd`.
5. На стадии Трейдер: медианный месячный доход, вероятность дожить до N выплат.
6. Классика (вторично): PF, winrate, avg R, max DD, Sharpe/Sortino, число сделок, доля комиссий в PnL.
7. Доля неоднозначных внутрибарных исходов (SL и TP в одном баре), отчёт качества данных (раздел 3.2).

### Monte Carlo
- **Rolling start:** запускать отдельный челлендж с каждого дня истории (после окна сброса, в 20:10 UTC) по фактическим данным → распределение исходов без перемешивания. Брать **только стартовые дни, после которых в данных есть ≥ H дней**: иначе прогоны обрываются концом истории и смещают оценку.
- **Block bootstrap** дневных последовательностей сделок (блоки 3–5 дней) → доверительные интервалы для P(pass).
- Стресс-сценарии:
  - комиссии ×1.5, slippage ×2;
  - случайный пропуск 10% сигналов (человеческий фактор при ручном исполнении);
  - задержка исполнения ×2;
  - equity по last price;
  - funding ×1.5 (ставка HashHedge неизвестна).

### Исследование гипотез (два уровня)
- **Уровень 1 — векторный скрининг** (`quant/research`).
  - Для каждого сигнала: метка тройного барьера (что наступило раньше: TP, SL или таймаут за `max_hold_bars` на 1m, с консервативной внутрибарной логикой раздела 5) и MFE/MAE.
  - Быстрые метрики (winrate, avg R, EV в R) по сотням вариантов входов.
- **Уровень 2 — событийный бэктест с propsim** — только для короткого списка кандидатов.
- **Выходы оптимизируются отдельно от входов** по сохранённым MFE/MAE: ATR-трейлинг, частичный TP, тайм-стоп, перенос в безубыток.
- Каждый проверенный вариант (на любом уровне) пишется в реестр испытаний.

### Оптимизация
- Целевая функция: максимизировать P(pass both) в пределах H (или EV) при ограничении P(fail by daily) ≤ порога. Доходность сама по себе целью не является (раздел 10).
- **Walk-forward:** окна train/test (по умолчанию 6 мес / 2 мес, шаг 2 мес) с **purge + embargo ≥ `max_hold_bars`** между train и test, т.к. метки сделок перекрывают границу окна. Последние 6 месяцев данных — **hold-out, не трогать** до финальной проверки.
- Параметры — пулом по группам (правило 3.1.7), а не по символу.
- **Поправка на множественное тестирование.** По числу испытаний из реестра в отчёте считаются Deflated Sharpe Ratio и PBO (CSCV). При большом переборе одного сравнения с baseline недостаточно.
- Ограничить число свободных параметров; штраф за нестабильность параметров между окнами; отчёт о чувствительности (плато, а не пик).
- Сравнение режимов: риск на сделку {0.25, 0.5, 0.75, 1.0}% × `flatten_before_reset` × наборы фильтров.

### Отчёт
HTML-отчёт на прогон:
- параметры, метрики (включая unresolved);
- кривые equity для выборки челленджей;
- гистограммы дней до прохождения и причин провала;
- таблица walk-forward;
- сравнение с baseline;
- DSR/PBO, доля неоднозначных баров, отчёт качества данных;
- хэш датасета и версия кода.

## 8. Live-режим: вероятности, интерфейс, Telegram

### 8.1 Откуда берётся вероятность (обязательно)

«Вероятность» в интерфейсе — **не** сырой score 0–100, а откалиброванная историческая частота успеха похожих сетапов.

- Определение успеха: для сигнала с планом (entry, SL, TP) — **TP достигнут раньше SL** в пределах `max_hold_bars`, с учётом комиссий и консервативной внутрибарной логики (раздел 5). Ничья по таймауту — отдельный исход.
- Для каждого сигнала бэктестера сохранять: признаки (все компоненты score, режим рынка, asset_class, ТФ, side), исход и MFE/MAE.
- Калибровка `score → P(win)`: изотоническая регрессия (или Platt) **только на out-of-sample сделках walk-forward (с purge/embargo)**, отдельно для long и short, с группировкой crypto major / crypto alt / tradfi. Модели версионируются в Postgres.
- Для каждой вероятности показывать: **P**, 95% доверительный интервал (Wilson), **n** — число исторических сделок в корзине, **EV в R** = `P × RR − (1 − P) − fees_R`. При `n < 100` (параметр) — вместо процента «мало данных».
- P(long) и P(short) **не дополняют друг друга до 100%**: обе могут быть низкими → «вне рынка».
- До завершения фазы 5 вероятности не показываются: только score с пометкой «не откалибровано».
- Контроль качества: reliability diagram, Brier score, сравнение предсказанной и фактической частоты на live-сигналах (скользящее окно); если расхождение > порога — алерт «калибровка устарела», вероятности помечаются серым до переобучения.
- Позже (опционально, после фазы 5): gradient boosting (LightGBM) на тех же признаках с той же схемой калибровки и walk-forward с purge/embargo; внедрять только если Brier/EV на hold-out лучше изотонической модели.

### 8.2 Сигнальный цикл

- `signals` читает Redis Streams, на закрытии бара каждого ТФ пересчитывает индикаторы, score и вероятности для всех инструментов; публикует снапшот в Redis (hash на символ + pub/sub канал `screener`).
- Сигнал создаётся, только если одновременно:
  - P ≥ `min_prob`, EV ≥ `min_ev_r`, `n` ≥ `min_n`;
  - risk governor разрешает (лимиты счёта, soft daily stop, корреляция, лимиты HashHedge);
  - нет активного сигнала по этому символу/стороне;
  - бар не `halted`, сейчас не окно сброса 20:00–20:10 UTC;
  - для TradFi — идёт сессия базового рынка (если `tradfi_off_session_signals: false`).
- Жизненный цикл сигнала: `new → active → (triggered | expired | invalidated) → (tp | sl | timeout)`; все переходы в Postgres; исход отслеживается автоматически по рыночным данным даже если сделка не взята (для контроля калибровки).
- Состояние счёта: ручной ввод через UI или Telegram (`/balance`, `/equity`, `/pos add|close`), несколько челленджей; встречные позиции между счетами запрещены. Equity и запас до лимитов система считает сама — по mark price и введённым позициям, не полагаясь на дашборд HashHedge (он обновляется не в реальном времени).

### 8.3 Интерфейс (web)

**Экран 1 — Скринер (главный).** Таблица всех инструментов из `instruments.csv`, live-обновление через WebSocket.
- Колонки: символ, класс, цена, изменение 24h, HTF-тренд (стрелка/цвет), RSI(14), ADX, расстояние до VWAP (%), ATR%, funding, ΔOI 24h, CVD-тренд, **score long / score short**, **P(long) % / P(short) %** (с ДИ в тултипе), **EV (R)**, статус (активный сигнал / наблюдение / нет / вне сессии / halted), лимит HashHedge (`max_per_lot`).
- Переключатель ТФ (15m / 1h / 4h), фильтры: класс актива, только сигналы, min P, min EV, только лонг/шорт; сортировка по любой колонке; сохранение пресетов.
- Цветовая индикация: зелёный/красный по стороне, насыщенность по P; серый — «мало данных», «не откалибровано» или «вне сессии».
- Шапка: состояние выбранного челленджа (см. экран 3) — запас до дневного и общего лимита в $, время до ресета (окно 20:00–20:10 UTC).

**Экран 2 — Инструмент.**

- **Панель анализа:**
  - вероятности long/short с ДИ, n и EV;

  - статистика этого сетапа из бэктеста: n, winrate, средний R, ДИ, последние 10 исходов.
- Контекст: funding/OI график, BTC-тренд (для альтов), для TradFi — статус сессии базового рынка.

**Экран 3 — Счета.** Список челленджей: стадия, баланс/equity (ручной ввод), прогресс к цели, торговые дни, запас до дневного/общего лимита, soft stop, открытые позиции. Режим `target_lock` подсвечивается.

UI-требования: тёмная/светлая тема, адаптив (скринер читаем с телефона: на узком экране — карточки вместо таблицы), время в UTC и локальном поясе пользователя (переключатель).

## 9. Фазы и критерии приёмки

**Фаза 1 — каркас и правила.** Репозиторий, конфиги (pydantic-схемы, включая одностадийный челлендж), перенос `instruments.csv` в `config/`, `propsim` + все тесты из 2.6 (включая mark-price equity, окно сброса, funding от mark price).
*Приёмка:* все тесты зелёные, покрытие propsim ≥ 90%.

**Фаза 2 — данные.** Загрузчик и валидатор `instruments.csv` (раздел 3.1) и проверки раздела 3.2. Backfill из data.binance.vision (+ Bybit REST для кросс-проверки) в Parquet с манифестом → ClickHouse (DDL). Нормализация множителей, gap-detector, детектор `halted`.
*Приёмка:*
- все 172 тикера проходят валидацию или помечены с причиной;
- данные до `history_start` не загружаются (тесты на LITUSDT и PUMPUSDT);
- детектор `halted` находит замороженный период LITUSDT (ноябрь–декабрь 2025);
- все архивные файлы сверены с CHECKSUM;
- максимально доступная история 1m с `history_start` по каждому инструменту;
- 0 гэпов с причиной `unknown`;
- повторная загрузка того же периода не меняет агрегаты старших ТФ (тест на дубли);
- расхождение Binance↔Bybit по нормализованной цене в пределах порогов 3.1.5;
- rebuild из Parquet воспроизводит таблицы;
- unit-тест нормализации для 1000-контрактов.

**Фаза 3 — индикаторы и стратегии.** Библиотека индикаторов с golden-тестами, `baseline_random`, `confluence_v1`.
*Приёмка:* паритет с TradingView по правилам раздела 6; тест на отсутствие look-ahead (сдвиг будущих данных не меняет сигналы прошлого).

**Фаза 4 — бэктест, MC, отчёты, векторный скрининг.**
*Приёмка:*
- санити-чек модели (теория — задача о разорении: 10/(10+8) = 0.556): `baseline_random` на синтетическом ряде-мартингале (случайное блуждание 1m) даёт P(pass stage1) = 0.556 ± 3σ MC при условиях:
  - фиксированный риск 0.5% на сделку, R:R 1:1;
  - нулевые комиссии, funding и slippage;
  - неограниченный горизонт, все прогоны завершены;
- с risk governor по умолчанию на горизонте 90 дней доля fail ≈ 0 при большой доле unresolved — ожидаемое поведение, отдельный тест;
- на реальных данных baseline только отчитывается (ожидаемо чуть ниже из-за правила «SL первым»);
- отчёт генерируется одной командой.

**Фаза 5 — оптимизация.** Walk-forward с purge/embargo, стресс-тесты, реестр испытаний, финальная проверка на hold-out.
*Приёмка:* отчёт сравнения с baseline с доверительными интервалами, DSR/PBO по реестру испытаний.

**Фаза 6 — калибровка и live-сигналы.** Калибровка score→P на OOS-сделках (8.1), Python-collector, Redis Streams, signals, Telegram-бот, Grafana, docker-compose.
*Приёмка:*
- reliability diagram на hold-out в пределах ±5 п.п. по корзинам с n≥100;
- 7 дней непрерывной работы без потерь данных (сверка live-баров с архивом T+1: 0 необъяснённых расхождений);
- сигналы live совпадают с бэктестом на тех же барах.

**Фаза 7 — интерфейс.** FastAPI (REST + WS), Vue 3 SPA — экраны 1–5 (8.3), авторизация, Caddy.
*Приёмка:* скринер 172 инструментов обновляется ≤ 2 с после закрытия бара; все числа в UI совпадают с API/БД (e2e-тест на Playwright); вход только с TOTP.

**Фаза 8 (позже).** Рынок US Stocks (`market=us_stocks`) — отдельная платформа HashHedge:
- только двухстадийный челлендж, размеры $5k–100k;
- buying power = balance × 5 на весь счёт;
- до 10 000 акций на тикер;
- блокировка новых позиций в 23:55 UTC+4, автозакрытие в 23:59 UTC+4;
- граница дня 04:00–04:10 UTC;
- комиссия 0.04%, минимум $1.

Нужны источник данных (Polygon/Alpaca/Databento), календарь сессий, учёт сплитов и дивидендов.
